# claude_pptx_making 設計書（ドラフト v0.2）

> 目的：**Claude に「〇〇の資料を pptx で」と頼んだとき、毎回ゼロから組まずに、一定以上の品質（密度・整合性・編集しやすさ）の pptx を短時間で出せる土台**を作る。
> 対象リポジトリ：`sibyl2501/claude_pptx_making`（現在は空）

---

## 0. 前提：調査で分かったこと

### 0-1. ChatGPT 版（`consulting-pptx-templates`）の評価

15 枚の見本を PowerPoint で書き出して確認した。構成（結論見出し・出典欄・章ラベル）や JSON 入力・数式対応などの**骨格は良い**。一方で、品質が足りないと感じる原因は次の 6 点にあると判断した。

| # | 課題 | 具体的な症状 |
|---|---|---|
| 1 | **下半分が空く** | 15 枚中 8 枚以上で、本文が上 50〜60% に収まり下が空白。本文は 9〜11pt 程度と小さく、「余白はあるのに文字は小さい」状態 |
| 2 | **グラフが図形の寄せ集め** | 線・四角・文字で描いているため、PowerPoint で数値の編集・グラフ種類の変更ができない |
| 3 | **レイアウト（マスター）が 1 種類だけ** | 全ページ白紙レイアウトに直接配置。プレースホルダーがなく、色やフォントを一括で変えられない。アウトライン表示も機能しない |
| 4 | **視覚的な強弱が弱い** | ほぼ 1 色（緑）＋細字テキスト。「結論ボックス」「数値の強調」「図解」が少なく、読み手の目が止まる場所がない |
| 5 | **パターンがコンサル報告書寄り** | 学習資料・解説資料（今回の NN 資料のような「式＋図＋カード」）に使える型がない |
| 6 | **自前の XML 書き出し（545 行）** | 保守が重く、文字の収まりの見積もりも粗い |

### 0-2. 参考記事（パワポ研「コンサル・シンクタンクのスライド 30 選」）から取り入れる原則

記事は具体的な数値ルールではなく、各社スライドの特徴の講評。設計に効くのは次の 5 つ。

1. **情報量が多くても「構造化＋上下左右の整列」でスッキリ見せる**（マッキンゼー型）→ グリッド厳守
2. **密なページは「枠（ボックス）」で区切り、余裕のあるページは罫線を最小限に**（BCG・EY 型）→ 密度に応じて 2 系統のスタイル
3. **1 色相の濃淡で階層を作る**（KPMG 型）→ テーマは「主色 1＋濃淡＋アクセント 1」
4. **グラフを主役に置き、周辺は簡素に**（MURC・MRI 型）→ グラフパターンは図 6〜7 割
5. **事実を積み上げて結論へ**（シンクタンク型）→ アクションタイトル（結論を言い切る見出し）＋根拠

### 0-3. 今回の NN 資料で効いたこと（そのまま設計に入れる）

- 1 枚に**カード 6 枚＋補助パネル**の高密度構成でも、グリッドと色の統一で読める（濃色の黒板パネルはテンプレートでは採用せず、白背景＋枠線の `Panel` にする）
- `$数式$`・`**太字**`・`^{上付き}`・`_{下付き}` の**ミニ記法**で、日本語と数式の混在を簡潔に書ける
- **ネイティブグラフ**（PowerPoint で編集可）＋考察ボックス
- **PowerPoint で PDF 化 → 画像で目視確認**のループで、はみ出し・孤立文字を潰せた

## 1. 設計方針（5 原則）

| 原則 | 内容 | ChatGPT 版の課題との対応 |
|---|---|---|
| **P1. 密度は「埋める」前提** | 各パターンは本文領域の 85% 以上を使う設計。空きが 25% を超えたら警告し、「内容を足す／型を変える」を促す | #1 |
| **P2. すべて編集可能** | テーマ色・テーマフォント・スライドレイアウト（プレースホルダー）・ネイティブグラフ・ネイティブ表で構成 | #2 #3 |
| **P3. 1 枚 1 メッセージ** | 全ページ共通で「アクションタイトル（結論）＋リード文＋本文＋出典」。結論ボックスを標準部品にする | #4 |
| **P4. 用途を 2 系統で持つ** | 「ビジネス・報告（コンサル型）」と「学習・解説（講義型）」の両方のパターンを揃える | #5 |
| **P5. Claude が使う前提** | 仕様書（JSON）→ 生成 → 自動検査 → 画像確認 → 修正 の手順を Skill として同梱し、次回以降の会話で自動的に使われる | #6 |

## 2. ページ設計（共通の骨格）

### 2-1. 用紙とグリッド（既定：**A4 横** 297 × 210 mm ＝ 11.69 × 8.27 in）

```
┌──────────────────────────────────────────────────────┐ 0.00 in
│ 章ラベル（9pt, 主色）                                  │ 0.22
│ アクションタイトル（22pt 太字, 1行・最大2行）           │ 0.30–0.90
│ リード文（12pt, 補色）                                 │ 0.90–1.20
├──────────────────────────────────────────────────────┤
│                                                      │
│   本文領域  x: 0.45–11.24 in / y: 1.30–7.75 in        │
│   （幅 10.79 in × 高さ 6.45 in）                       │
│   12 カラム（列幅 0.74 in, 段間 0.17 in）              │
│   ブロック間の間隔は 0.15 in に統一                     │
│                                                      │
├──────────────────────────────────────────────────────┤ 7.80
│ 出典・注記（8.5pt, グレー）               ページ番号   │ 7.85–8.10
└──────────────────────────────────────────────────────┘ 8.27
```

- 16:9 と比べて横は約 12% 狭く、縦は約 13% 広い（本文領域の高さ 5.70 → 6.45 in）。縦に積むパターン（カード 3 段、表、ロジックツリー）を標準にし、横 4 列以上のパターンは列数を 1 つ減らした変種を既定にする
- 16:9 ワイド（13.333 × 7.5 in）にも `"size": "16:9"` で切り替え可能。座標はすべてグリッド単位で定義し、用紙サイズから計算する（本文領域 x: 0.45–12.88 / y: 1.30–7.00 in）
- 余白：左右 0.45 in、本文と出典の間 0.05 in 以上
- 印刷・PDF 配布を前提に、**本文ページに濃色の面は使わない**（濃色背景は表紙・章扉のみ）。強調は淡色の面・主色の枠線・アクセント色の文字で行う

### 2-2. 文字サイズ（2 モード）

| 要素 | `dense`（読む資料・既定） | `present`（発表用） |
|---|---|---|
| アクションタイトル | 22pt 太字（A4）／24pt（16:9） | 32pt 太字 |
| リード文 | 12pt | 16pt |
| カード見出し | 13pt 太字 | 18pt 太字 |
| 本文 | 10.5–11pt（下限 9.5pt） | 14–16pt（下限 14pt） |
| 表 | 10pt | 12pt |
| 出典・注記 | 8.5pt | 10pt |

- 本文は**枠に合わせて自動で上限〜下限の間で調整**。下限でも収まらない場合は生成を止めてページ・要素名を表示
- フォント：和文 **ヒラギノ角ゴシック**（本文 W3、太字 W6）、欧文はヒラギノの欧文をそのまま使う、数式 **Cambria**、等幅 **Menlo**（Windows では Consolas に置き換え）。テーマフォントの東アジア枠（`ea`）にも設定する（今回の資料では未対応だった点）
  - ヒラギノは Mac 専用。Windows で開くと別のフォント（多くは游ゴシック／MS ゴシック）に置き換わり、折り返し位置が変わる。Windows で使う予定の資料だけ `"font": "yu-gothic"` で游ゴシックに切り替える
  - 太字の指定方法（太字属性で W6 になるか、W6 を書体名で指定するか）は Phase 1 の最初に Mac 版 PowerPoint で確認して決める
  - 文字の収まり計算（`text-fit.js`）はヒラギノの字幅テーブルを既定にする

### 2-3. 色（テーマで一括管理）

- 構成：**主色 1（60–70%）＋その濃淡 2＋アクセント 1＋中立グレー**。色の役割は意味で固定する

| トークン | 用途 |
|---|---|
| `primary` / `primary-dark` / `primary-tint` | 見出し・表の見出し行・パネルの枠線・カード背景 |
| `accent` | 番号バッジ・強調・グラフの注目系列（1 枚に 1〜2 か所まで） |
| `positive` / `negative` | 増減・○×・良否 |
| `ink` / `muted` / `rule` | 本文・補足・罫線 |

- 初版で 4 テーマを用意：**Forest**（学習：深緑＋琥珀、今回の資料の配色）、**Navy**（報告：紺＋橙）、**Graphite**（技術：墨＋青緑）、**Burgundy**（提案：えんじ＋金）
- テーマ切替は 1 行（`"theme": "navy"`）。PowerPoint の［デザイン → バリエーション］でも変えられる

## 3. 部品（コンポーネント）

すべてのパターンは、以下の部品の組み合わせで作る。部品は位置・大きさをグリッドで受け取り、色はテーマトークンだけを使う。

| 部品 | 役割 | 由来 |
|---|---|---|
| `ActionTitle` / `Lead` / `ChapterLabel` | ページ上部の 3 点セット（レイアウトのプレースホルダー） | 共通 |
| `Card` | 番号バッジ付きの見出し＋箇条書き。淡色背景、縁取りなし | NN 資料 |
| `Panel` | 白背景＋主色の細い枠線（0.75pt）＋主色の見出し。数式・形状ルール・読み方など、カードと性格の違う補足をまとめる | NN 資料の黒板を置き換え |
| `KeyMessage` | 「つまり何か（So what）」を 1〜2 行で示す帯 | 新規 |
| `Table` | 縞模様、見出し行は主色、強調列、○△× 記号の自動着色 | 両方 |
| `Chart` | ネイティブグラフ（棒・折れ線・積み上げ・散布・複合・円）。軸・凡例・文字の見た目を全グラフで統一 | NN 資料 |
| `KpiTile` | 大きな数字（40–60pt）＋ラベル＋前年比 | 新規 |
| `StepFlow` | 番号付きの手順・矢印（横／縦） | 新規 |
| `Timeline` | ガントバー・マイルストーン | ChatGPT 版を改良 |
| `Tree` | ロジックツリー・イシューツリー（コネクタ線） | 新規 |
| `Matrix2x2` | 軸ラベル付きの 4 象限 | 新規 |
| `IconCircle` | 色付き円の中のアイコン（react-icons を PNG 化） | 新規 |
| `Diagram` | ノードとリンクの簡易図（ネットワーク図・構成図） | NN 資料 |
| `Source` | 出典・注記（レイアウトのプレースホルダー） | 共通 |

### ミニ記法（すべてのテキストで共通）

| 書き方 | 結果 |
|---|---|
| `**強調**` | 太字 |
| `==強調==` | アクセント色 |
| `$W^{T}x + b_{i}$` | 数式フォント（Cambria）＋上付き・下付き |
| `[[3.0℃]]` | 数値の強調（太字＋主色） |
| 行頭 `- ` | 箇条書き、行頭 `  - ` で 2 段目 |

### D. 計画・実行系
| ID | パターン | 使う場面 |
|---|---|---|
| D1 | `roadmap` | ガント（担当・時期・到達点） |

| ID | パターン | 使う場面 |
|---|---|---|
| E1 | `concept_map` | 概念の対応表＋流れ（NN 資料 1 枚目） |
| E2 | `chart_cards` | 左にグラフ＋`Panel` で読み方、右にカード（NN 資料 3 枚目） |

|---|---|---|
| F1 | `references` | 参考文献・用語集 |

## 5. 入力仕様（デッキ仕様 JSON）

```json
{
  "deck": {
    "title": "線形代数×微分積分で読み解くニューラルネットワーク",
    "theme": "forest",
    "size": "a4",
    "density": "dense",
    "author": "…"
  },
  "slides": [
    {
      "pattern": "card_grid",
      "chapter": "線形代数",
      "title": "線形代数：ニューラルネットの「骨格」",
      "lead": "1つの層は「線形変換＋平行移動＋非線形関数」",
      "grid": "2x3",
      "cards": [
        { "title": "ベクトルと内積＝類似度",
          "body": ["- $w·x = ‖w‖‖x‖cosθ$", "- ニューロンは**類似度**を測る"] }
      ],
      "panel": { "title": "形状で見る z = Wx + b", "body": ["- $(m×n)(n×1) = (m×1)$"] },
      "source": "出典：…",
      "notes": "話す内容・解答など"
    }
  ]
}
```

- JSON Schema（`schema/deck.schema.json`）でパターンごとの必須項目・範囲を検査
- Claude は「目的・読み手 → ストーリー（1 枚 1 メッセージ）→ パターン選択 → JSON 記入」の順で作る

## 6. 自動検査（QA）

| 段階 | 内容 | 道具 |
|---|---|---|
| 1. 入力検査 | スキーマ・容量・未対応記法 | `ajv` |
| 2. 文字の収まり | フォントの実寸（ヒラギノの字幅テーブル、切替時は游ゴシック）で行数を見積もり、自動縮小／停止 | `text-fit.js` |
| 3. **密度検査** | 本文領域に対する使用面積。空き 25% 超で警告（ChatGPT 版の最大の弱点への対策） | `density.js` |
| 4. ファイル検査 | PowerPoint が開けない XML を検出 | `validate.py`（pptx Skill） |
| 5. 目視確認 | PDF 化 → 画像化 → 一覧画像。Mac は PowerPoint、他は LibreOffice | `render.sh` |

## 10. Phase 1 の実装メモ

設計からの変更点と、実装で確かめたこと。

- **パターンは 1 ファイル（`src/patterns.js`）にまとめた。** 10 パターンでは 1 ファイルの方が見通しがよいため。Phase 2 で数が増えたら分割する
- **色は生成時に HEX で埋め込み、同じ配色をテーマにも書き込む。** pptxgenjs ではテーマの配色スロットを参照できない箇所（表・グラフ）があるため。PowerPoint で図形を追加するときは、テーマの配色から同じ色を選べる
- **ヒラギノの太字：** 書体名 `Hiragino Sans` に太字属性を付けると W6 で表示される（Mac 版 PowerPoint で確認）
- **字幅の実測値：** 行送り＝文字サイズ×1.2、和文 1.0em、欧文平均 約 0.54em。`src/config.js` の `METRICS` に反映
- **JSON Schema（`schema/deck.schema.json`）は Phase 2 に回した。** Phase 1 では `build.js` の入力検査（必須項目・パターン名）で代用
- **`exec_summary` の根拠カードは本文の上限を 2pt 上げた。** 要約ページの主役で、上限 12pt では空きが目立ったため
- 「1〜2文字だけの最終行」の自動検出は未実装（Phase 2）。現状は `qa/render.sh` の画像で確認する

## 11. Phase 2 の実装メモ

- **25 パターンすべてを実装。** 1パターン1ファイル（`src/patterns/`）に分け、共通部品を `_shared.js` にまとめた
- **全パターンの見本 `examples/catalog.json`**（架空の需要予測導入の事例、27ページ）を追加。A4／16:9、dense／present、4テーマ、游ゴシックで生成し、PowerPoint で開けることを確認
- **入力の仕様（JSON Schema 2020-12）** を `src/schema.js` で定義し、`schema/deck.schema.json` に書き出す。未知の項目名（書き間違い）もエラーにし、どのスライドのどの項目かを日本語で示す
- **1〜2文字だけの最終行の検出。** 段落ごとに最終行の文字数を見積もり、0.5〜1pt 小さくして減るなら自動で調整、残りは警告
- **空きが目立つときの拡大。** グループ内のすべての枠が半分ほどしか埋まらないとき、本文を 2pt まで大きくする（細い列の `cheat_sheet` は除く）
- **壊れた図形の検出。** 大きさが負の図形があると PowerPoint が「修復」を求めて開けなくなる（Phase 2 の途中で実際に発生）。書き出し後に全スライドを調べ、見つかれば生成を止める
- **`data_table` の改ページは行を均等に分ける。** 最後のページだけ数行になるのを避ける
- **滝グラフ** は積み上げ棒（白い土台の系列）で作るネイティブグラフ。小さすぎる棒の数値は条件付き書式で隠し、`invert` で増減の色を入れ替えられる
- **回帰テスト（`npm test`）**：見本3本の仕様検査・はみ出しなし、catalog を5つの設定で生成、全パターンの使用、記法と収まり計算の単体テスト

### 既知の制限

- 発表向け（present）で dense 用の見本をそのまま生成すると、文字が入りきらない枠が出る（警告で分かる）。発表向けは1枚の情報量を減らして書く
- `matrix_2x2` の `items` の点は座標どおりに置くため、象限の文字と重ならない位置（各象限の下半分）を指定する
- 文字の収まりは見積もりのため、PowerPoint の実際の折り返しと数％ずれることがある。最終確認は `qa/render.sh` の画像で行う

## 12. Phase 3：Claude Code の Skill 化

- **目的。** 記録（メモリ）はフォルダごとにしか効かず、汎用の pptx 作成手順が先に呼ばれるとキットが使われない。Skill として登録し、どのフォルダ・どの会話でも資料作成の依頼で自動的にキットを使わせる
- **構成。** `skill/pptx-making/SKILL.md`（手順書）、`scripts/setup.sh`（キットの取得・更新と依存の準備）、`scripts/example.sh`（指定パターンの実例を1枚だけ取り出す）
- **登録。** キットを `~/claude_pptx_making` に置き、`~/.claude/skills/pptx-making` からキット内の `skill/pptx-making` へリンクする。キットを更新すれば Skill も更新される
- **呼ばれ方。** 説明文（description）に「新規の資料作成ではこちらを優先、既存 pptx の編集は汎用 pptx スキル」と書き、役割を分ける
- **読む量。** 手順書（約3千トークン）＋使うパターンの実例だけを読む。README・見本全体（1.5万〜2万トークン）を毎回読む必要がなくなる
